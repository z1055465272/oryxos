# Feature Specification: Tool 体系 — Agent 能动手干活的手

**Feature Branch**: `020-lesson20-tool`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "第20节需求：Tool 体系——让 Agent 真正能动手干活的手。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 内置工具让 Agent 读写文件、跑命令、调 API (Priority: P1)

用户问"今天北京天气怎么样、我该穿什么"（Demo 一的对话版），Agent 的 ReAct 循环里 LLM 决定调 `http_get` 查天气 API，OryxOS 执行请求、拿到 JSON 回填给 LLM，LLM 据此给穿搭建议。运维场景里 Agent 也可以读服务器上的日志文件、跑一条排查命令。这些能力来自 OryxOS 内置的一批基础工具：文件类（读/写/列目录）、Shell（跑命令）、HTTP（发请求）。调用方（ReAct 循环）只按统一工具形态请求，不关心工具背后是文件操作、子进程还是 HTTP 客户端。

**Why this priority**: 内置工具是 Agent 从"只会说"到"能干事"的最短链路，覆盖"读写文件、跑命令、调 API"这三大类基础动作，是 Demo 一和后续所有业务 Agent 的依赖。必须最先交付。

**Independent Test**: 对每个内置工具，构造合法输入调用执行，断言拿到非空成功结果；再构造越界输入（白名单外的路径/命令/域名），断言被安全校验拦下抛错。两个用例分别验证"功能对"和"踩不出边界"。

**Acceptance Scenarios**:

1. **Given** 一个读取文件的内置工具，**When** 传入一个在允许路径白名单内的文件路径，**Then** 返回该文件的成功读取结果（含内容）。
2. **Given** 一个读取文件的内置工具，**When** 传入一个不在允许路径白名单内的路径，**Then** 执行被安全校验拦下并抛错，文件没有被真正读取。
3. **Given** 一个执行命令的内置工具，**When** 传入一条在命令白名单内的命令，**Then** 返回命令的执行结果。
4. **Given** 一个执行命令的内置工具，**When** 传入一条不在命令白名单内的命令，**Then** 执行被拦下并抛错。
5. **Given** 一个发起 HTTP 请求的内置工具，**When** 传入一个在域名白名单内的 URL，**Then** 返回响应体。
6. **Given** 一个发起 HTTP 请求的内置工具，**When** 传入一个不在域名白名单内的 URL，**Then** 执行被拦下并抛错，请求没有真正发出。

---

### User Story 2 - 统一工具抽象与注册，让任意来源的工具对循环透明 (Priority: P1)

OryxOS 的工具来源五花八门——内置的、业务方用 Java 写的、通过外部 MCP server 接进来的。如果 ReAct 循环要按来源区别对待，代码会很快乱掉。于是需要一个统一工具抽象：不管工具从哪来，都包装成同一种形态注册进同一个注册表，ReAct 循环只跟这种统一形态打交道，完全不感知它背后是什么。

**Why this priority**: 统一抽象是整个 Tool 体系的地基。它决定"三种来源的工具以同一种身份注册、按需过滤、循环无感调用"这个核心能力是否成立。与 P1 同为最核心交付，因为它先于一切工具的具体实现。

**Independent Test**: 构造一个注册表，把代表三种来源的工具实例（模拟内置、Java 插件、MCP）都注册进去；再按一个声明了部分工具名的过滤条件，断言过滤出的子集恰好等于声明列表——不多不少（多一个说明没过滤干净，少一个说明过滤过头）。

**Acceptance Scenarios**:

1. **Given** 一个注册表，**When** 分别注册来自三种来源的工具（模拟内置 / Java 插件 / MCP），**Then** 三者都以统一的工具形态存在，注册表按名称能查到每一个。
2. **Given** 一个注册表里已注册若干工具，**When** 按一个 Profile 声明的工具列表过滤，**Then** 返回的子集恰好等于该列表——不多一个、不少一个。
3. **Given** 一个已注册的工具，**When** 检查它的契约三件套（名称 / 描述 / 参数说明），**Then** 三件套都非空——任何工具漏了参数说明，调用方在翻译成模型格式时就会卡死。

---

### User Story 3 - 业务方通过 MCP server 接入自己的工具（方式二），失联不拖垮启动 (Priority: P2)

业务方用任意语言写一个 MCP server，在 `.oryxos/mcp_servers.yaml` 里声明它（name / transport / command / env），OryxOS 启动时自动连上这个 server，把它的工具列表（tools/list）逐个包装成统一工具形态注册，Agent 就能调。如果某个 server 连不上或配置错了，OryxOS 记一条警告、跳过它的工具、其余 server 照常注册、启动照常完成——外部依赖的可用性不是自己的可用性。

**Why this priority**: MCP 接入是 Plugin Tool 方式二（轻代码）的核心，也是方式一（零代码复用社区 MCP server）的底层支撑。它排在内置工具之后，因为它依赖统一抽象和注册表先就位。失联隔离是这条链路上最容易被忽略但最重要的行为——不隔离，一个外部 server 挂了会拖垮整个 OryxOS 启动。

**Independent Test**: 用 mock 的 MCP 客户端，模拟一个"工具列表能正常返回"的 server 和一个"连接/列出工具直接抛异常"的 server；调用连接入口后，断言好的 server 的工具已注册、坏的 server 的工具没有注册、且整个过程不抛异常。

**Acceptance Scenarios**:

1. **Given** 一个能正常连接的 MCP server，它的工具列表返回两个工具，**When** 执行连接注册，**Then** 这两个工具都被包装注册进注册表。
2. **Given** 一个正常的 server 和一个失联的 server（连接/列出工具抛异常），**When** 执行连接注册，**Then** 失联 server 只记警告、其工具不注册、正常的 server 的工具照常注册、整个过程不抛异常。
3. **Given** 一个已注册的 MCP 工具，**When** 调用它的执行，**Then** 调用参数被原样转发给外部 server，返回结果被包装成统一结果形态。

---

### User Story 4 - 重代码方式三：Java @Tool 注解 Bean 自动注册 (Priority: P3)

业务方在工程里写一个带 `@Tool` 注解的 Java Spring Bean，OryxOS 启动时自动扫描、生成参数说明、注册进注册表，Agent 就能在进程内直接调用——不走 MCP 协议、不起独立进程、不序列化。19 节的 `notify` 内置工具也在此完成 @Tool 注册接线，与其余内置工具一视同仁。

**Why this priority**: 方式三是门槛最高的接入方式，适合需要直接调用企业内部 Java 服务、复用现有 Spring Bean 的场景。它复用同一套统一抽象和注册机制，只是来源不同，因此是"方式一/方式二都就位后"的锦上添花，优先级最低。

**Independent Test**: 在 Spring 上下文中注册一个带 `@Tool` 注解的示例工具，启动后断言它在 `tool list` 可见（人工确认项）；自动化层面断言注册表里能查到它以统一工具形态注册、契约三件套齐全。

**Acceptance Scenarios**:

1. **Given** 一个带 `@Tool` 注解的 Java Bean，**When** OryxOS 启动扫描，**Then** 它被生成参数说明并注册进注册表，契约三件套齐全。
2. **Given** 注册表里已含 `notify` 工具，**When** 遍历所有已注册工具，**Then** 每个工具的契约三件套（名称 / 描述 / 参数说明）都非空。

---

### Edge Cases

- 工具执行的第一步必须是安全校验：校验不过直接抛异常拦下，真实的文件读取 / 子进程执行 / HTTP 请求根本不发生（白名单不能被绕过）。
- 某个 MCP server 失联时只记警告、跳过它，不能变成自己的启动故障；其余 server 照常注册。
- MCP 工具执行时，调用参数要原样转发给外部 server，返回结果要统一包装成结果形态（成功 / 失败 / 错误信息 / 是否可重试）。
- 安全校验组件在本阶段是占位实现（默认放行），但调用链已就位，工具执行第一步就过这一层——具体白名单逻辑由后续章节替换实现。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供统一工具抽象，约定四个方法——工具名、用途描述、参数说明（JSON Schema）、执行（接收 JSON 输入返回统一结果）。任何来源的工具（内置 / 注解插件 / MCP）都必须实现全部四个方法。
- **FR-002**: 工具执行结果必须携带四样信息：成功标识、结果内容、错误信息、是否可重试（供上层决定失败是否值得再调一次）。
- **FR-003**: 系统必须提供统一工具注册表：把三种来源的工具都以统一工具形态注册进来，按名称查找，并按 Profile 声明的工具列表过滤出该 Profile 可用的子集，子集必须恰好等于声明列表（不多一个、不少一个）。
- **FR-004**: 系统必须提供文件类内置工具（读文件 / 写文件 / 列目录），每个工具执行第一步先过安全校验，校验不过抛错拦下、不执行真实 IO。
- **FR-005**: 系统必须提供 Shell 内置工具（执行命令，带超时），执行第一步先过安全校验（命令白名单），校验不过抛错拦下、不真正执行命令。
- **FR-006**: 系统必须提供 HTTP 内置工具（GET / POST 请求），执行第一步先过安全校验（域名白名单），校验不过抛错拦下、不真正发请求。
- **FR-007**: 系统必须提供 MCP 客户端：启动时读取 MCP server 配置（name / transport / command / env），连接每个 server、获取其工具列表，把每个工具包装成统一工具形态注册进注册表。
- **FR-008**: 某个 MCP server 连接失败或获取工具列表失败时，系统必须只记警告、跳过该 server 的工具、其余 server 照常注册，且整体不抛异常（外部依赖的可用性不是自己的可用性）。
- **FR-009**: MCP 工具执行时，调用参数必须原样转发给外部 server，返回结果必须包装成统一结果形态。
- **FR-010**: 系统必须支持 MCP server 配置文件（声明 name / transport / command / env），配置缺失不阻断其余 server 的连接注册。
- **FR-011**: 安全校验组件以接口方式接入工具执行链路（工具执行第一步），本阶段为占位实现（默认放行），具体白名单逻辑由后续章节替换实现。
- **FR-012**: 三种 Plugin Tool 接入方式（零代码复用 MCP / 轻代码自写 MCP server / 重代码 Java 注解 Bean）必须在系统中并存，共用同一套统一抽象和注册机制。

### Key Entities *(include if feature involves data)*

- **统一工具抽象（OryxTool）**: 所有工具的统一接口形态——名称、描述、参数说明、执行方法，屏蔽工具来源。
- **工具执行结果（ToolResult）**: 一次工具执行的结果——成功标识、结果内容、错误信息、是否可重试。
- **工具注册表（ToolRegistry）**: 统一管理所有工具——注册（三种来源）、按名称查找、按 Profile 工具列表过滤子集。
- **MCP 工具适配器（McpToolAdapter）**: 把外部 MCP server 暴露的工具适配成统一工具形态，执行时经 MCP 协议转发。
- **MCP 客户端服务（McpClientService）**: 启动时连接所有配置的 MCP server、获取工具列表、包装注册，处理失联隔离。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注册表里每个已注册工具都能通过自动化遍历验证契约三件套（名称 / 描述 / 参数说明）非空，缺任何一项即测试失败——任何新工具漏实现参数说明立刻暴露。
- **SC-002**: 按 Profile 工具列表过滤的子集与声明列表精确一致，可通过自动化断言验证"不多不少"，多一个或少一个都失败。
- **SC-003**: 每个内置工具（文件 / Shell / HTTP）的"正常能跑通 + 越界会被拦"两条行为都可自动化验证，无需外部网络依赖。
- **SC-004**: MCP 失联隔离行为可自动化验证：失联 server 只记警告、其工具不注册、其余工具照常注册、整体不抛异常——某个外部 server 挂了不会拖垮 OryxOS。
- **SC-005**: MCP 工具执行转发行为可自动化验证：参数原样转发、结果统一包装。
- **SC-006**: 现有自动化测试套件（前序节交付的测试）全部保持绿色，本节改动不破坏已有功能。

## Assumptions

- 安全校验（沙箱白名单）的具体逻辑由后续章节（23/24 节）实现，本节仅以接口调用形式接入工具执行链路（工具执行第一步），占位实现默认放行。
- 统一工具抽象、结果形态、注册表接口已在核心模块（oryxos-core）就位，本节交付注册表的具体实现与全部内置工具、MCP 组件。
- 工具执行结果走已有的审计记录路径（tool_invocations 表，17 节 ToolExecutor 已交付），不新增审计逻辑。
- 工具是否对某 Agent 可见由 Profile 的 tools 字段过滤决定（结合统一注册表），完整的 allow/deny Tool Policy 放扩展阶段。
- 一次响应里多个工具并行调用、工具按需加载、把 OryxOS 自己变成 MCP server 对外暴露——均不在本节范围（扩展阶段）。
- MCP server 配置存于工作区 `mcp_servers.yaml`，采用手工维护的 YAML，不做独立数据库表和 CRUD API。
- `notify` 内置工具（19 节交付）在本节完成 @Tool 注册接线，与其余内置工具一视同仁进入注册表。
