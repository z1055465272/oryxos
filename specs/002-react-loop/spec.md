## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单轮问答快速响应 (Priority: P1)

用户通过任意触发源向 Agent 发一条不需要工具就能回答的问题（如"你好，介绍一下自己"），Agent 的推理引擎调一次大模型后直接返回最终回复，中间不执行任何工具，一轮收尾。

**Why this priority**: 这是 ReAct 循环的最短路径——没有工具调用时一轮即收尾，验证了"模型判断不需要工具就直接回答"这个核心停止条件。如果这步不工作，后续所有多轮场景都跑不起来。

**Independent Test**: 模拟 LLM 返回无工具调用的响应，断言推理引擎恰好调一次 LLM、返回内容与模型响应一致、未触发任何工具执行。

**Acceptance Scenarios**:

1. **Given** 用户消息"介绍一下自己"和已配置的 Agent 配置，**When** 推理循环开始执行，**Then** 调一次大模型、拿到响应后一轮返回最终结果，不执行任何工具。
2. **Given** 用户消息为空字符串，**When** 推理循环执行，**Then** 仍正常组装上下文并调用一次 LLM 返回结果，不崩溃。

---

### User Story 2 - 多轮工具调用完成任务 (Priority: P1)

用户问"今天北京天气怎么样，我该穿什么"，Agent 第一轮调 LLM 决定调用查天气工具，执行工具拿到 JSON 结果后进入第二轮，模型看到天气数据后给出穿搭建议并返回最终响应。

**Why this priority**: 这是 ReAct 的完整闭环——Reason（想）→ Act（做）→ Observe（看）→ 再 Reason 直到完成。多轮工具调用是 Agent 区别于 chatbot 的关键能力。

**Independent Test**: 模拟 LLM 第一次返回"要调天气工具"、第二次返回"建议穿羽绒服"的文本响应；模拟工具执行返回天气数据。断言推理循环调了两次 LLM、一次工具执行器，最终响应是第二次的文本。

**Acceptance Scenarios**:

1. **Given** 用户消息需要工具才能回答，**When** LLM 第一轮返回工具调用请求，**Then** 工具执行器执行工具、结果回填到会话、进入第二轮继续推理。
2. **Given** 工具执行完成后 LLM 第二轮不再要求工具，**When** LLM 返回纯文本，**Then** 推理循环结束并返回最终响应。

---

### User Story 3 - 工具调用死循环安全兜底 (Priority: P1)

Agent 陷入"每轮都要调工具、永不收敛"的循环（例如模型出现幻觉反复调同一个工具），系统在达到最大轮数（默认 10）后强制停止，返回清晰的停止提示，不会无限消耗 token 和计算资源。

**Why this priority**: 这是课件点名的最重要坑之一（坑一：死循环）。没有上限兜底，一次对话可能把用户 token 用光，在生产环境这是致命问题。

**Independent Test**: 模拟 LLM 永远返回带工具调用的响应（永不收敛），配置最大轮数为 10。断言循环恰好转了 10 轮、返回消息包含停止提示。

**Acceptance Scenarios**:

1. **Given** 模型每轮都要求调工具且最大轮数为 10，**When** 循环转了 10 轮，**Then** 强制停止、返回停止提示。
2. **Given** Agent 配置了更小的最大轮数（如 5），**When** 模型持续要求调工具，**Then** 最多 5 轮就强制停止。

---

### User Story 4 - 每轮对话完整可审计 (Priority: P2)

一次会话完成后，会话里记录了每一轮 LLM 说了什么、每次工具调用入参和返回结果。即使某次工具调用失败（如查天气超时），审计记录也包含失败标记和错误原因，不会静默丢失。

**Why this priority**: 这是审计 Day One 写入原则在本节的具体落地，也是课件坑三（不累积就无法审计）。审计完整性是 OryxOS 企业级定位的核心差异。

**Independent Test**: 跑完一次多轮对话后，断言会话的对话历史里包含了所有轮的 LLM 响应和工具调用结果；模拟一次工具执行失败，断言审计写入了一条失败记录且带错误原因。

**Acceptance Scenarios**:

1. **Given** Agent 执行了 2 轮 LLM 调用和 1 次工具调用，**When** 循环结束，**Then** 会话对话历史包含 2 条 LLM 响应和 1 条工具结果。
2. **Given** 某次工具执行抛出异常，**When** 工具执行器处理该异常，**Then** 审计写入失败标记且错误信息包含异常原因，异常继续上抛不吞。

---

### User Story 5 - 统一编排入口支持三种触发源 (Priority: P2)

CLI、Web API、定时任务三种触发方式都通过同一个处理入口进入，编排层负责在调用前后设置和清理线程上下文（ProfileContext），保证工具执行时能取到当前 Agent 的配置。

**Why this priority**: 这是课件"三种触发源共用同一入口"的架构约束。线程上下文泄漏是课件点名的最阴险 bug——在单请求测试里永远不报错，只在并发复用时串号。编排层的正确性直接影响后续所有节的可靠性。

**Independent Test**: 调统一处理入口，验证处理期间线程上下文可取到当前 Agent 配置；模拟循环执行抛异常，验证 finally 块清掉了线程上下文（断言其为空）。

**Acceptance Scenarios**:

1. **Given** 一个会话和用户消息，**When** 调统一处理入口，**Then** 处理期间线程上下文返回当前 Agent 配置、处理结束后线程上下文被清空。
2. **Given** 循环执行中抛异常，**When** 异常向上传播，**Then** 线程上下文仍然被清掉（finally 块执行），会话仍被尝试持久化。

---

### User Story 6 - 上下文实时更新无缓存 (Priority: P2)

运维人员修改了 Agent 的指令文件或某个启动文件后，下一次对话立即使用新内容，无需重启。同时，如果 Agent 配置引用了不存在的文件，系统给出明确的错误或警告而非静默跳过。

**Why this priority**: 课件指出静默跳过"人格悄悄丢了"是最难查的软故障。无缓存设计保证 Agent 行为的可调试性和即时生效能力。

**Independent Test**: 调用上下文供给两次，中间修改被读取的文件内容，断言第二次读到的是新内容。配置一个不存在的启动文件路径，断言产生告警级别日志；配置一个不存在的技能引用，断言报错。

**Acceptance Scenarios**:

1. **Given** 某个启动文件内容为"A"，**When** 第一次读取后文件被修改为"B"，**Then** 下一次组装立即读到"B"。
2. **Given** Agent 配置的启动文件列表包含不存在的路径，**When** 上下文供给加载时，**Then** 至少输出告警级别日志，不阻断整体上下文组装。
3. **Given** Agent 配置的技能引用指向不存在的技能，**When** 上下文供给加载时，**Then** 报错（非告警）。

---

### Edge Cases

- 最大轮数设为 0 或负数时，循环如何处理？（应至少执行一轮后判断，或启动前校验）
- 历史轮数设为 0 时，对话历史部分是否完全为空？
- 用户消息为空时，角色设定和历史是否仍正常组装？
- 可用工具列表为空时，工具列表部分是否产生合理输出（不崩溃）？
- 会话对话历史已为空（首次对话）时，截断逻辑是否不抛异常？
- 工具执行器收到一个不存在的工具名称时，返回包含错误信息的失败结果而非抛异常。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 循环调度——系统接收会话、用户消息与 Agent 配置，循环执行"组装上下文→经 Provider 调大模型→判断是否有工具调用"，无工具调用即返回最终答复，有则把工具逐个交给执行器执行并把结果回填后再进入下一轮，直到无工具调用或达到最大轮数（默认 10）。

- **FR-002**: 上下文组装——每轮按固定顺序组装发给模型的上下文：①角色设定+启动信息+技能（末尾附当前日期时间，模型自己不知道今天几号）②长期记忆（未就位时留空）③最近 N 轮对话历史（默认 20，超出截断）④当前可用工具列表。

- **FR-003**: 工具执行与审计——模型要求调用的工具被集中执行（执行权只此一处，不得有第二条执行路径），每次执行无论成败都写审计记录——成功标成功、失败带原因，异常不吞。

- **FR-004**: 统一编排——CLI、Web、定时三种触发源共用同一个处理入口，入口处把当前 Agent 配置放进线程上下文，处理结束（含异常路径，finally）必须清理该上下文，不泄漏。

- **FR-005**: 上下文供给——按 Agent 配置读取启动文件与技能文件：启动文件（Bootstrap）缺失至少 WARN 不阻断，技能文件（SKILL.md 正文）预载拼入 system prompt，显式引用的技能缺失必须报错（不静默跳过）；每次组装 prompt 都重新读文件不缓存（改完立即生效）。

- **FR-006**: 审计关联——循环每次调大模型与执行工具都携带会话标识，保证审计记录能按会话追溯。

- **FR-007**: 消息累积——每轮大模型响应与工具执行结果都累积回会话对话历史，事后完整可审计，下一轮也接得上前一轮。

### 明确不做（边界）

- 工具并行调用——一次响应里多个工具调用按顺序执行，不并行（扩展阶段再放开）。
- Agent 之间互相委托。
- 流式输出。
- 上下文压缩——先用"只留最近 N 轮"的简单截断顶着，压缩留到扩展阶段。
- 长期记忆模块未就位时，上下文第二部分留空（不因记忆缺失阻断对话）。

### Key Entities

- **ToolInvocation（审计记录）**: 记录一次工具调用的完整信息——关联的会话、工具名称、输入参数、执行结果、成功/失败标识、错误信息、执行耗时、创建时间。成功与失败都写入。
- **Session（会话）**: 本节使用其对话历史累积能力和关联的 Agent 名称来驱动循环和审计关联；正式持久化建模在后续节，本节先以内存形态承载。
- **Prompt（一次 LLM 调用的输入）**: 承载发给模型的完整上下文——角色设定、多轮消息、当前可用工具列表（扩展既有形态以支持多轮，向后兼容）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单轮无工具调用场景下，循环恰好调一次 LLM 并在一轮内返回最终结果。
- **SC-002**: 多轮工具调用场景下，循环能正确完成"调 LLM → 执行工具 → 回填 → 再调 LLM → 最终响应"的完整闭环。
- **SC-003**: 模型持续要求调工具时，循环恰好转最大轮数后强制停止，一轮不多。
- **SC-004**: 每次 LLM 调用和工具执行都在审计记录里有对应条目（成功和失败都记），可通过会话标识关联追溯。
- **SC-005**: 修改启动或技能相关文件内容后，下一次上下文组装立即读到最新内容，无缓存延迟。
- **SC-006**: 统一处理入口在正常结束和异常退出两种情况下都能清掉线程上下文，不泄漏。
- **SC-007**: 所有自动化测试（五个单测类）通过，构建门禁全绿。

## Assumptions

- 前置依赖：第 16 节交付的 Provider 抽象（能按会话标识发起一次大模型调用、成功/失败都写审计）、Agent 配置（含最大迭代轮数、历史轮数、工具、启动信息、技能配置）、Profile 注册表已就位可用。
- 会话持久化（会话管理接口的完整实现、sessions 表）由后续节交付，本节先定义会话管理契约供编排层依赖；若接口不存在，本节先定义最小接口。
- 工具注册表由后续节（Tool 体系）交付，本节先定义查找契约，测试时以替身注入。
- 沙箱检查由后续节（Sandbox 体系）交付，本节工具执行留调用位并注明接线节次，不自行实现。
- 长期记忆模块由后续节（Memory 体系）交付，本节上下文组装的记忆部分留空位。
- 项目使用 Java 21 + Spring Boot 3.x + Spring AI Alibaba，同步阻塞模型，配合虚拟线程；凭证走环境变量，不在代码或配置文件中硬编码。
- 外部依赖无新增：复用既有 Spring AI BOM 与 SQLite 手工建表脚本（tool_invocations 表 DDL 已在既有脚本中预留）。
- 跨节改造（用户裁定接受）：本节向后兼容扩展第 16 节交付的 Prompt 值对象（新增 system prompt 与多轮消息承载，保留旧构造器）并适配 Provider 实现（`chat` 签名不变，改为发送完整消息序列）；这是第 17 节课件 FR-002 四部分上下文强制的改造点。
