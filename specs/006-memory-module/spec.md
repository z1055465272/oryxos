# Feature Specification: Memory 模块 — Agent 记得住事

**Feature Branch**: `022-lesson22-memory`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "第22节需求：Memory 模块——三层记忆统一门面 + 文件式长期记忆 + 两个内置记忆 Tool。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 主动记住值得长期保留的事（save_memory）(Priority: P1)

对话里用户说了一句值得长期记住的话（比如"以后推荐用 Java"）。Agent 判断这件事值得记，主动调用"记住"这个能力，把内容连同"这条是核心记忆还是归档记忆"的归类写进长期记忆文件。写入之后，从下一轮起，每次组装系统提示都会把长期记忆带进去——同一进程内立刻生效，不用重启、不用等下一次冷启动。核心记忆这一类是"始终在场"的：无论后来记了多少归档流水，它都不会被挤掉或截断。

**Why this priority**: "记得住"是 Memory 能力的最核心一环，也是 Demo 二（每日科技日报体现用户偏好）的触发条件。没有写入，后面的读取和检索都是空谈。必须最先交付。

**Independent Test**: 调"记住"能力写入一条归档记忆，随后立刻读取长期记忆并断言这条内容出现；再用"按关键词检索"能力搜同一个词，断言命中。同一进程内完成，验证"记完立刻生效"。

**Acceptance Scenarios**:

1. **Given** 一个空白的长期记忆文件，**When** 写入一条归档记忆（含具体内容），**Then** 同进程内下一次读取长期记忆时，这条内容立即可见。
2. **Given** 同上，**When** 用这条内容的某个关键词发起检索，**Then** 检索立即命中该条。
3. **Given** 长期记忆文件，**When** 写入一条核心记忆，再持续写入大量归档记忆把归档区灌到超过容量上限，**Then** 读取时核心记忆仍一字不少地出现，而归档区最早的内容被裁掉、最近的内容保留。

---

### User Story 2 - Agent 按关键词从长期记忆里捞回相关条目（recall_memory）(Priority: P2)

需要时，Agent 想知道"用户之前说过什么偏好"这一类问题，它调"按关键词检索"的能力，传入一个关键词，拿到命中归档记忆的条目列表；如果一条都没命中，返回一句"没有找到相关记忆"，而不是报错中断。检索只在归档区做——核心记忆反正每次都完整在场，不需要"找回来"这个动作。

**Why this priority**: "读得出"是记忆闭环的第二环。检索做得朴素即可（关键词包含匹配），核心目标是稳定可用、未命中不报错。

**Independent Test**: 先写入若干条归档记忆，再分别用"能命中的词"和"注定命不中的词"发起检索，断言前者返回命中条目、后者返回"没有找到相关记忆"的提示而不抛异常。

**Acceptance Scenarios**:

1. **Given** 长期记忆文件里已写入包含某关键词的归档条目，**When** 用该关键词检索，**Then** 返回包含该关键词的归档条目。
2. **Given** 长期记忆文件里没有任何含某关键词的条目，**When** 用该关键词检索，**Then** 返回"没有找到相关记忆"，不抛异常。

---

### User Story 3 - 会话记忆与长期记忆在系统提示里合成"记忆上下文"，重启不丢 (Priority: P3)

每次 Agent 处理一轮对话，系统提示里既带当前会话的历史，也带长期记忆（核心记忆 + 截断后的归档记忆）。长期记忆来自文件，进程重启后文件还在，新会话仍然读得到——记忆天然跨进程存活。写入长期记忆的归类由 Agent 显式说明（默认当归档），系统不自作主张替它猜。

**Why this priority**: "合成上下文"把两层记忆统一成一份给模型的输入，"重启不丢"验证文件式存储的持久性。优先级 P3 因为它是 P1/P2 之上的组装与验证，不单独构成可用闭环。

**Independent Test**: 组装一轮对话的上下文，断言其中同时含核心记忆与当前会话历史，且归档区内容不整体注入（只以截断后的形态存在）。进程重启后重新读取，断言此前写入的记忆仍在。

**Acceptance Scenarios**:

1. **Given** 已写入若干核心记忆与归档记忆、且有一个含若干消息的会话，**When** 组装本轮上下文的记忆部分，**Then** 返回内容同时含核心记忆与会话历史，归档区不整体注入。
2. **Given** 已写入若干条记忆，**When** 重新启动进程后再次读取长期记忆，**Then** 记忆内容仍然存在（文件天然跨重启）。

---

### Edge Cases

- 长期记忆文件不存在（首次使用）时，读取应返回空内容而不是报错；写入应能自动创建文件。
- 归档区内容超过容量上限（4000 字）时，只裁归档区、核心区一字不动；最早的内容被裁掉、最近的内容保留。
- 写入归类参数缺失或非法时，按"归档"处理（系统不猜核心，也不因参数异常而中断写入）。
- 检索关键词为空时，返回空命中，不抛异常。
- 记忆文件为空或只有核心区时，读取与检索都不崩溃。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的记忆门面，对外暴露三件事——给 Prompt 组装用的"记忆上下文"（核心记忆 + 会话历史）、给 Agent 用的"记一条"和"按关键词查一下"。
- **FR-002**: 系统 MUST 将长期记忆持久化到一个 Markdown 文件，内部按二级标题分两个区块：核心记忆区与归档记忆区；两个区块读写规则不同。
- **FR-003**: 核心记忆区 MUST 永远完整返回、不被截断、不换出；截断 MUST 只作用在归档区。
- **FR-004**: 长期记忆 MUST 每次读取都重新读文件，不做任何缓存（写入后同一进程内立即可见）。
- **FR-005**: 写入长期记忆的区块 MUST 由调用方经"归类"参数显式指定（核心或归档），缺省按归档处理；系统 MUST 不自作主张猜归类。
- **FR-006**: 按关键词检索 MUST 只在归档区做简单包含匹配（不引入分词/正则等复杂化），命中返回匹配条目。
- **FR-007**: 归档区超过容量上限（4000 字）时 MUST 截断，只裁归档区文本，核心区一字不动。
- **FR-008**: 检索未命中时 MUST 返回"没有找到相关记忆"的提示，而不是抛异常。
- **FR-009**: 系统 MUST 把长期记忆拼进每次组装 Prompt 的上下文（与角色设定、会话历史、工具列表并列）。

### Key Entities

- **长期记忆文件（MEMORY.md）**: 一条按 Markdown 二级标题分区的长期记忆文件，两个区块——核心记忆区（永远完整）与归档记忆区（可截断、可检索）。每条记忆带日期标记。
- **记忆条目归类（MemoryScope）**: 核心（CORE）与归档（ARCHIVAL）两类，决定写入哪个区块。
- **会话（Session）**: 前序已交付的会话记忆载体，由统一门面作为"会话历史"一部分合成记忆上下文。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 写入一条归档记忆后，同一进程内立即读取即见（无缓存），立即检索即命中——100% 用例通过。
- **SC-002**: 归档区被灌到超过容量上限后，读取结果中核心记忆内容完整保留、最早归档条目被裁掉、最新归档条目保留——100% 用例通过。
- **SC-003**: 检索未命中的关键词返回"没有找到相关记忆"提示而不抛异常——100% 用例通过。
- **SC-004**: 记忆上下文同时含核心记忆与会话历史，归档区不整体注入——100% 用例通过。
- **SC-005**: 进程重启后，此前写入长期记忆文件的内容仍然存在并可读。

## Assumptions

- 长期记忆文件的默认位置是 `.oryxos/memory/MEMORY.md`（工作区规范目录）。
- 核心阶段只交付 Markdown 文件式长期记忆这一种实现；可插拔后端接口（Sqlite/Mem0）与后端切换配置留扩展阶段，不列入本节。
- 写入归类默认按归档处理；归类参数语义为"核心 / 归档"二选一。
- 会话记忆复用前序已交付的会话管理能力，本节只在其上做统一门面合成。
- 记忆检索为朴素的关键词包含匹配，不做语义检索、不做自动抽取、不做记忆压缩算法。
- 记忆文件缺失时按空内容处理，首次写入自动创建文件。
